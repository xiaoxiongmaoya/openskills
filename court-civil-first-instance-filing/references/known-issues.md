## 1 确认必须回读法院，不能用本地值

**现象**：确认时贴的是"我准备提交什么"（案由 `民间借贷纠纷`），法院实际存 `laay=002004001031004`。用户看着正常就提交了。

**根因**：确认单由本地 spec 渲染，没回读 `layy`。本地意图与远端真值之间恰好隔着字段写反、PATCH 覆盖这类错误。

**修正** `scripts/confirm_filing.py` → `client.confirm_snapshot()`，逐项判定并给正确对照值：案由名称/id 是否配对、`dsrMc` 是否含角色、必传槽是否齐、两项决策是否落值。

---

## 2 案由字段写反 → 前台显示编码

**现象**：案由显示 `002004001031004`。

**根因**：字段语义与直觉相反：

| 字段 | 正确值 | 错误写法 |
| --- | --- | --- |
| `laay` | 名称，如 `民间借贷纠纷` | 编码 `002004001031004` |
| `laayMz` | 节点 id，如 `9181` | 名称 |

`002004001031004` 是节点 `fjm`，`9181` 是同一节点的 `id`。接口都返回 200，只是前台拿 `laay` 直接渲染。

**修正** `client.save_cause(filing_id, "民间借贷纠纷")`；`precheck` 拦截"laay 是纯数字 / 以 0020 开头"。

---

## 3 参与人不显示「原告/被告」

**现象**：列表显示 `张三、李四`，正常单是 `原告：张三；被告：李四`。

**根因**：`layy.dsrMc` 是前端拼好随 layy 提交的展示串，不是后端按当事人实时算。只 `POST dsr` 不写它，就只剩名字。

**修正** 写完当事人调 `sync_dsr_mc()`，格式 `原告：A，B；被告：C`（中文逗号分多人、分号分角色）。

---

## 4 账户确认书传错槽 → 「其他材料」为空

**现象**：文件已关联到「收款账户确认书」槽（`11800016-36`），接口 200，前台看不到。

**根因**：模板有槽位 ≠ 前台可见。审核侧按「其他材料」口径检查。

**修正** 除 36 槽外再传一份到 `11800016-3`，命名 `其他材料-账户确认书.pdf`。runner 已自动双投。

---

## 5 `PATCH layy` 是全量覆盖

**现象**：只 PATCH `{"id","sqbdje"}`，之前写好的 `laayMz`、`ajmc` 变 null。

**修正** 一律走 `patch_layy(updates)`：先 GET 详情做底、合并、再整对象 PATCH。不要裸 `patch_filing` 写单字段。

---

## 6 材料 `ssclid` 用错值

**修正** 必须用草稿详情 `data.sscls[].id`（每单生成的 uuid），不是模板 `pz/layymb` 里的 `"1"~"7"`。

---

## 7 案由树必须 GET + `lbs`

- `GET /api/v1/ay/tree/batch?lbs=0300`（民事案由）可用。
- `POST` → 405；缺 `lbs` → 400。
- 节点：`id` → `laayMz`，`fjm` → 编码（前台不用），`name` → `laay`。

## 8 先行调解：必须问，字段易丢

**必问**：`tjpz` 返回 `sfkt`（是否走该流程）、`title`、`tsy`（告知原文，直接转给用户）。
排期数 `GET layy/sjzt/ajpqtj/count/{fyid}`（某区法院实测 N 件），前台原话：
`您好，您将向{fymc}提交立案申请，在您的案件之前有{N}件案件正在排期等待开庭审理。请问您是否考虑选择先行调解？`

**落库字段** `layy.lasfzsqt`：`1501_000010-1` 同意 / `-2` 不同意。

**实测结论（三条路都留不下痕迹）**：
- 独立 `PATCH /api/v3/layy` 带 `lasfzsqt` → 200，回读 null。
- 放进 `PATCH /layy/submit` 的完整 layy 对象 → 提交成功，回读 null。
- 前台选「接受调解」后复制草稿提交 → 回读 null。

同时排查过 `satj`（是"网上立案"立案方式，不是调解）、`zctj`、`sfysla`、`ysxxs`、`shpcs`，均无调解选择。

**判断**：弹窗内容由后端 `tjpz` 下发（不是纯前端写死），但**用户的选择没有持久化到立案单任何可读字段**。实务上当"提示性问卷"看待——不影响立案单数据，也不能用来回查用户选了什么。
做法：问用户 → 记本地 `case.json` 的 `decisions.mediation` → 需要真正生效就走法院前台。不要写 `lasfzsqt`，也不要拿它判断。

**坑**：字段为空 ≠ 用户没选。复制草稿提交（`layyIdy` 非空）还会在账号下留两张同案单。

## 9 被告身份证照片必须单独确认

- 身份信息（姓名、证件号、住址）**可以照填**。
- 照片**必须单独问**，与调解同级；不得默认、不得与身份信息合并成一个问题。
- `precheck` 校验 `decisions.defendant_id_photo`（upload/skip）；选 upload 时还要核对槽内有「被告」文件。
- 决策写入 `05案件信息/case.json`（带时间戳）。

## 10 验证码 OCR 不可用（根因：onnxruntime 版本）

**实测（本机 Win10 19045 / Python 3.13.14 / numpy 2.5.4 / ddddocr 1.6.1）**：

- `onnxruntime 1.31.0`、`1.22.1` 加载即失败：`OSError: [WinError 1114] 动态链接库(DLL)初始化例程失败`，`onnxruntime.dll` 的 DllMain 就挂了，所以 `try/except` 拦不住（在沙箱里表现为 access violation / exit 139）。
- **降到 `onnxruntime==1.20.1` 后正常**：`import ddddocr` 通过，真实 `captcha.png` 识别出 4 位码。
- 与沙箱、CPU、VC 运行库无关：`onnxruntime_providers_shared.dll` 可加载，`cv2`/`fitz` 也正常，只有 `onnxruntime.dll` 的 1.22+ 构建在本机初始化失败。

**修复**：`pip install "onnxruntime==1.20.1" ddddocr coloredlogs sympy`（`--no-deps` 装 ORT 时必须补 `coloredlogs`/`sympy`，否则 `pip check` 报缺）。

**不要升级 ORT**：`>=1.22` 在本机必挂；升级前先跑导入探针。

其余要点：
- `input()` 兜底在无 stdin 环境会卡死；非交互一律 `dump_captcha()` → 视觉识别 → `login_with_captcha(captcha_id, code)`。
- `login(captcha_code=...)` 旧实现会重新取码导致 id 错配，已修。验证码 `id` 一次性。
- OCR 仍建议放子进程跑（崩溃不带走进程），但本机修复后已能在主进程直接使用。

## 11 客户乱包：乱码 + 分类不清

- Windows 打包多 GBK，Python 按 cp437 解会乱码；按 `flag_bits & 0x800` 判断，否则 `cp437→gbk` 还原。
- 解压只落 `01原始包/解压/`；分类是**复制**，原件不动。
- 已签 PDF → `02签字件`；图片 → `03图片件`；Word/未签 PDF → `04未签稿`。
- 命名 `序号-材料名-页序.ext`（序号对齐法院槽位），上传后前台不显示 uuid。
- 无线索文件（uuid 命名）按父目录兜底（`原告/`、`被告/`）；仍认不出的列 `unrecognized`。

## 12 代理律师必须上传律师证

**规则**：只要是代理律师代为立案，`委托代理人委托手续和身份材料` 槽（`11800016-9`）必须含**律师执业证**扫描件，与授权委托书、律所函并列。

**坑**：法院模板里该槽 `isbx=2`（非必传），容易被当成"可传可不传"。实务上律师立案缺证会被要求补正。

**修正**：
- `precheck` 已加硬校验：有代理人记录时，槽内文件必须含「律师证」或「执业证」，否则报错中止。
- `organize_materials` 已加规则：文件名含 `律师证`/`执业证` → 规范名 `03-律师执业证.pdf`，归入 `02签字件`。

## 13 只读 Word，不拿扫描 PDF 当数据源

**现象**：某案读扫描版起诉状 PDF，把本金 `200000` 认成 `20000`、被告「李明」认成「李朋」、原告证件号 `…1990******0011` 认成 `…1990******0012`，差点按错值立案。

**根因**：签字 PDF 是图片，无文本层；OCR 对相似字形和连续数字不可靠。

**规则**：
- 当事人姓名、证件号、金额、诉请**只从 Word 原稿取**（`read_office_text.py`，支持 .doc/.docx）。
- PDF **不解析**，只作为上传件；需要核对时人工看图。
- 整理材料时 Word 必须留在 `04未签稿/`，即使同时存在签字 PDF。
- 身份证照片只用来定人；与文书冲突时以证件为准并提示用户。

## 14 要素式诉状没写受理法院

**现象**：部分诉状模板（要素式）落款不写「此致 XX 人民法院」，无法直接确定 fyid。

**处理**（`suggest_court.py`）：

1. 先找文书里的「XX人民法院」，命中就直接用（诉状常省略省市，如「某某区人民法院」，按区县名检索再匹配全称）。
2. 找不到则按管辖顺序给候选：
   - 被告住所地（一般地域管辖，民诉法第 22 条）
   - 合同履行地——民间借贷以「接收货币一方所在地」为履行地，即原告住所地
3. 地址取词：从「某省某某县…」「某某市某某区…」里剥掉省/市前缀，只留区县（用「某某市」检索会命中一堆区法院）。
4. 级别管辖：标的额超基层上限时提示可能需中院。
5. **输出候选 + 依据 + fyid，交用户拍板**，不自动建档。

## 15 `filing_id` 不回写 → 复跑重复建档

**现象**：先 `--apply` 停在提交前，再 `--apply --submit`，法院账号下出现**两张同案草稿**，材料也重传了一遍（每案多 80+ 次请求）。

**根因**：`filing_id` 只写进 `case.json`（给人看），`spec.json` 从不回写；第二次运行读到 `filing_id=""` 就走新建草稿分支。

**修正**：建档成功即回写 spec（`filing_runner._write_back_filing_id`），复跑走「复用草稿」分支。要重开单就手动删 spec 里的 `filing_id`。

## 16 401 直接抛错 → 整条链断

**现象**：token 过期后，`confirm_filing.py` / `query_filing.py` 直接报「会话已失效」，需要人工重新登录。

**根因**：`request_json` 遇 401/403 只清会话再抛错，不重试、不重登；且 `_clear_session` 会 `unlink` 会话文件，多 worker 共用时把别人一起登出。

**修正**：401 只清本进程内存 → 自动重登一次（`_relogin_in_progress` 防递归）→ 重放原请求；会话文件改原子写，删除改为显式 `purge_file=True`。

---

## 17 审核意见永远 null：字段找错地方

**现象**：状态已经是「审核未通过」「补充材料」，`query_filing.py` 输出的 `review_opinion` 仍是 `null`，
于是误判成「法院端没填审核意见」，只能叫用户登录网站自己看。12 案实测全空。

**根因**：脚本取的是 `data.layy.shyj`——法院前端**从不往 layy 写这个字段**。
真正的审核结果在 `data.shjgs[]`（前端「审核结果」区块同源，见 wsla.js 渲染逻辑），每条 record：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `shjg` | 状态码 | `11800007-3` |
| `cshjg` | 审核结果文本 | `审查不通过` / `退回补充材料` / `审查通过` |
| `shyj` | **审核意见全文**（含邮寄地址、电话、补正清单，多行） | 数百字 |
| `shsj` | 审核时间 | `<yyyy-MM-dd HH:mm:ss>` |
| `shrxm` | 审核人 | `任洪明` |
| `bhyy` / `cbhyy` | 驳回原因码 / 文本 | `11800023-12` / `其他` |
| `thfjwjs` | 退回附件（`wjmc` + 带签名 `url`） | 法院给的要素式起诉状模板 |
| `bcclSj` | 材料补正时间 | 常见 null |

**修正**：`CourtClient.parse_review_records()` 抽取全部记录按时间倒序；`review_opinion` 取最新一条并回落 `layy.shyj`。
`query_filing.py` 先打印人读摘要（意见逐行照抄、分段保留），`--write` 时把 `thfjwjs` 下载到
`05案件信息/法院退回件/`（URL 带签名会过期，不存就永久丢失）。附件下载**不走 session**——
OSS 收到 `Authorization` 头会按签名字段校验直接 403。

**教训**：字段名看起来对不代表位置对。前端有展示、接口有数据，就一定能捞到；捞不到先翻前端 JS 的取值路径。

## 18 多线程上传 → OSS 403 / 「获取上传信息失败」

**现象**：`run_batch.py --workers 3` 跑两三个案子，传着传着开始报
`OSS 403`、`未获取到材料上传地址`；重跑又会整批重传，越传越慢，甚至把账号行为打成异常。

**原因**：上传是 `签名 → OSS 直传 → 关联槽位` 三步。全局令牌桶只管「平均 1 请求/秒」，
多个 worker 照样能在同一秒内各取各的签名、各传各的 OSS —— 请求速率没超，但**并发上传行为**超了。
这才是风控真正盯的东西。

**修正**：
- `court_client.UploadPacer`：跨进程文件锁（`<根>/通用件/.court_upload.state`）把整段上传**串行**，
  同一时刻全机器只有一个上传在跑；再加 `间隔 3.5s ± 抖动 1.5s`，每 6 份长停 25s。
- `run_batch.py --workers` 默认 1；上传阶段即使给大值也会自动降回 1（要强行并发得加
  `--allow-parallel-upload`，但上传仍会被锁串起来，只是多开进程没意义）。
- 参数 `--upload-interval / --upload-jitter / --upload-batch / --upload-cooldown`，
  环境变量同名可覆盖。

**教训**：风控看的不是「请求数」而是「行为像不像人」。并发上传再怎么限速也还是机器特征；
慢一点一次过，比快一点反复重传省时间。

## 19 重新提交立案换了 filing_id → 旧单意见全丢

**现象**：驳回后没法原地重提，只能人工在法院网页「复制立案」，这会生成**新的 layy id**。
`filing_runner` 把新 id 写回 `case.json` 顶层 `filing_id`，上一单的驳回意见、审核人、案号就被覆盖。
更麻烦的是**没人会告诉 skill 这个新 id**，于是本地永远停在旧单的「审核未通过」。

**修正**：`bind_filing.py` 维护 `case.json.filings[]` 链，换单不丢旧单：

```
filing_id        ← 当前有效单
filings: [{filing_id, status, review_at, reviewer, review_opinion,
           case_no, superseded_by, superseded_at, note}, ...]
```

- `filing_runner._write_back_filing_id()` / `_refresh_note()` 换 id 时自动调 `bind_filing.bind_new()`，
  旧单封存并写 `superseded_by`；换单后顶层 `status` 置「待查询」并清旧意见。
- 人工复制立案后，手工绑一次：`bind_filing.py --new-filing-id <新 id>`。
- `案件说明.md` 增加「立案单变更链」表格。

**放弃自动发现的理由（实测）**：本想用 `GET /api/v3/layy` 全量拉单再按指纹匹配自动认领，
探测后发现两处硬伤，不值得：

| 探测项 | 结果 |
| --- | --- |
| 账号规模 | 1631 张单，9 页（limit=200 可用，无 total 字段） |
| 排序 | **页内乱序**：第 1 页 71 处、第 2 页 86 处逆序断点，不能按时间提前停止 |
| 服务端过滤 | `fyid` / `kssj` / `jssj` / `ajlb` **全部无效**；只有 `zt`、`sfid` 生效 |
| 重复指纹 | 同一 (参与人, 案由) 最多 13 张单，唯一匹配是少数情况 |

结论：必须全量拉 9 页（约 10 秒）才能保证不漏，且冲突是常态，自动认领误配风险高（实测误配到外省法院）。
改为**人工指定一次 + 保留历史链**，成本更低、不会认错。

**教训**：一个案件目录在法院端可能是**多张单**，本地必须存一对多关系，不能只存一个 id。

- 建草稿后系统自动塞一条「申请人=登录律师本人、诉讼地位=原告」的当事人，必须删。
- **撤回**：已提交单撤回后会退回草稿状态（`zt=11800007-100`），立案单 id 不变；彻底删除后详情接口返回 500。

## 20 强制执行申请（zx）实测踩坑（个人账号）

执行立案复用 `layy`，但有 5 处必须在代码里区别对待，否则提交直接失败：

1. **执行请求/理由不在 `layy.ssqq`/`ssly`**：必须写进 `data.zxyjs[0].zxqq` / `.zxyjzw`（`PATCH /api/v3/zxyj`）。
   只写 `ssqq` 时提交报 `RMFY109905 提交网上立案信息失败`（message 泛化，看不出原因）。
2. **执行标的挂在 `zxyjs[0]`**：`sqzxbdzl`（种类，逗号分隔，金钱给付=`1501_100279-1`）+ `sqzxbdje`（金额）。
   `layy.sqzxbdzl` 服务端不回写，别指望从 layy 读。
3. **申请执行人的「住所地（户籍所在地）」`hjszd` 必填**：只写 `dz` 时列表显示「待补全」，
   前端校验提示「请填写住所地（户籍所在地）」。被执行人不需要。
4. **当事人要带角色字段**：`ssdwMc`（申请执行人/被执行人）、`ssdwType`（`yg`/`bg`）、`dsrType`（自然人 `zrr`）。
   `ssdw` 编码：申请执行人 `1501_100225-1`、被执行人 `1501_100225-2`（实测可用）。
5. **Word 原稿优先，执行案件不强制**：一审缺 Word 阻断，执行只打警告（必备材料是判决书 PDF /
   扫描件）。降级读 PDF 时，当事人与金额必须逐项人工核对。
   执行必传槽位：执行申请书 `11800016-2`、执行依据文书 `11800016-8`、申请人身份 `11800016-1`。

### 已定位：`RMFY109905` 的真凶是 `layy.ajmc` 为空

执行单不会自动生成案名，`ajmc` 空时「我的立案」列表显示**名称暂无**，提交一律报
`RMFY109905 提交网上立案信息失败`（message 泛化，看不出原因）。

补上案名立刻返回 `{"code":200,"message":"操作成功"}`，`zt` 变 `11800007-1`（待审核）。

- 案名格式：`{申请执行人}申请执行{被执行人}{原审案由}一案`，例 `王小春申请执行杨金海承揽合同纠纷一案`
- 代码位置：`sync_dsr_mc(case_type="zx", cause=原审案由)` 自动拼；`spec.case.ajmc` 显式给了就强制覆盖
- 门禁：`precheck` / `confirm_snapshot` 已把「案名为空」列为阻断项，不会再盲提交

排查时排除过的方向（都不是原因，别重复试）：建单字段、当事人角色、执行依据、
执行标的、审计字段、`sqzxbdzls`、`gyid`、执行申请书自动生成。
